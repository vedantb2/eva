# Elevated surfaces: use smooth-shadow-ring, never border + shadow

Adapted from [flornkm/shadow-plugin](https://github.com/flornkm/shadow-plugin)
(MIT). Read the eva notes at the bottom before applying — the utilities are
generated by a local Tailwind v3 port, not by the published package, and the
ring is wired to eva's own token.

## When this applies

Any element that floats above the page surface: cards, dialogs, modals,
popovers, dropdowns, menus, tooltips, sheets, toasts, command palettes.

## The problem

Putting a `border-*` (or `ring-*`) and a `shadow-*` on the same element draws
two stacked edges: the border paints a hard 1px stroke, and the shadow begins
just outside it. The result is a visible double border, a crisp line then a
soft one. It looks heavy, greyed, and cheap.

## The rule

If you are about to write a `border-*` or `ring-*` class next to any `shadow-*`
on an elevated surface, use `smooth-shadow-ring-{size}` instead. It bakes a 1px
hairline ring into the final shadow layer, so the edge dissolves into the shadow
as one continuous stroke.

- `border shadow-md` → `smooth-shadow-ring-md`
- `ring-1 ring-border shadow-lg` → `smooth-shadow-ring-lg`
- Sizes: `smooth-shadow-ring-xs`, `-sm`, `-md` (or bare `smooth-shadow-ring`), `-lg`, `-xl`, `-2xl`
- Never keep a `border` or `ring` on an element that already has
  `smooth-shadow-ring-*`. The ring is already in there; a second edge doubles up.
- If the surface should have no edge stroke at all, use plain
  `smooth-shadow-{size}` (no ring), not a border.

## What this does NOT apply to

The rule is about _elevated surfaces_. These keep real borders:

- **Layout-region dividers** — the sidebar edge, list/detail splits, table and
  menu separators, `border-b` on a header. These separate regions in the same
  plane; nothing is floating, so there is no shadow to double up against.
- **Form affordances** — inputs, selects, textareas, and the `InputGroup`
  wrapper. The border _is_ the affordance that marks the control as editable,
  and it changes colour on focus and on `aria-invalid`.
- **Accent bars and inset rules** — `border-l` status stripes, blockquote rules.
- **Focus rings** — `focus-visible:ring-2 ring-ring/35` is a state, not an
  edge. It coexists with `smooth-shadow-ring-*` on the same element.

## Coloring

The shadow tints via `--smooth-shadow-color`, which reads Tailwind's
`--tw-shadow-color` and falls back to black.

The ring reads `--smooth-ring-color`. Override it at any scope:

```css
.some-surface {
  --smooth-ring-color: rgb(var(--primary) / 0.4);
}
```

## Example

```tsx
// Wrong: border + shadow renders a double edge
<div className="rounded-surface border border-border bg-card shadow-md">…</div>

// Right: one continuous edge
<div className="rounded-surface bg-card smooth-shadow-ring-md">…</div>
```

## eva specifics

**The published `shadow-plugin` package cannot generate these classes here.**
It is Tailwind v4-only — its source is entirely `@theme`, `@utility` and
`--value()`, and eva is on tailwindcss 3.4.17. The package is in
`apps/web/package.json` as the provenance of the values; the utilities are
actually emitted by [`apps/web/tailwind-smooth-shadow.js`](../../../apps/web/tailwind-smooth-shadow.js),
a v3 port with identical class names and layer geometry.

Three differences from upstream follow from that:

1. **No `smooth-ring-{color}` utility.** It needs v4's `--value()`/`--modifier()`.
   Set the `--smooth-ring-color` variable instead, as shown above.
2. **No `!important`.** Upstream needs it to win v4's `@utility` ordering. Here
   it would defeat `tailwind-merge`, which does not know `smooth-shadow-md`
   conflicts with `shadow-sm`. **Never put a `shadow-*` and a `smooth-shadow-*`
   on the same element** — `cn()` will not dedupe them and the later rule in the
   stylesheet wins, not the later class in the string.
3. **The ring is wired to eva's `--border` token**, not upstream's hardcoded
   `rgba(0,0,0,0.05)` / `rgba(255,255,255,0.18)`. So a converted surface keeps
   exactly the edge weight it had as `border-border`, and all three appearances
   (`:root`, `.dark`, `.dark.neutral`) stay correct with one declaration —
   `.dark`/`.neutral` are set on `<html>`, the same element as `:root`.

`CLAUDE.md` still describes eva as border-first. That remains true for the
dividers and affordances listed above; elevated surfaces are the exception this
skill governs.
